# Give jobs a stable identity and bind runs to it for DDK build records

DDK-CATALOG-012 (data-design-kit main 2a44207) treats a DocSpec job as a production: identified by a declared id, versioned by the JobSpec's SHA-256, inputs/outputs mapped to catalog datasets, steps tied to their SQL. A run binds to the job when its pinned request keeps the job's input names, ordered steps (SQL, parameters, materialization) and outputs; only input bindings and scratch paths may differ. Today JobResult records output identities and native input observations but no job identity or exact input versions.

## Acceptance Criteria

JobSpec carries an optional stable job id; JobResult (and the managed receipt) name the job id, the JobSpec digest and each input's exact version or file digest; DDK's catalog attaches a run to a SpicyRegs dataset version through it (DDK WP-15 item 8 implemented against this).
