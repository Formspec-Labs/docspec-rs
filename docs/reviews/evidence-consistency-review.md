## Initial findings, retained with their dispositions above

### W1 — Plans can report receipt work that adoption has already eliminated

- Severity: **WARNING**; category: correctness of progress reporting.
- Location: `src/engine.rs:344`, `plan_request_admitted`; `src/engine/evidence.rs:240`, `inherit_receipts`.
- Evidence chain: a request with an evidence-bearing base unconditionally gains the `receipts` phase unless it is a schema or receipt operation. `inherit_receipts` returns the existing receipt table without a durable `receipts` completion when the source has the same logical identity or the applied source change removes no occurrences. Consequently, an insert-only update paused after validation has no receipt work to execute on resume, but its plan still lists `receipts` as required.
- Practical effect: this does not change values or receipts, but it misstates remaining work under RESEARCH UR-03.
- Suggested correction: when retained processing already proves the adoption branch, omit that phase from required work or report its adoption explicitly. Add one assertion on the paused insert-only plan.

### W2 — The new receipt-pruning completion lacks its own interruption test

- Severity: **WARNING**; category: test coverage / qualification.
- Location: `src/engine/evidence.rs:249`, `inherit_receipts`; `tests/evidence_updates.rs:283`, `receipt_processing_survives_process_loss_without_original_input`.
- Evidence chain: value corrections now create a separately recoverable `receipts` completion with the new source and previous receipt table as dependencies. The new process-loss test kills the **receipt-update operation after processing**, then removes the original receipt input and checks that admission and processing do not restart. It does not stop a **source update after its receipt-pruning completion**. The ordinary source-update test checks pruning and retention only after successful selection (`tests/evidence_updates.rs:143`).
- Practical effect: the implementation contains the needed reuse and retention paths, but their newly introduced handoff is not independently exercised. This is an unqualified recovery case, not evidence of a failure.
- Suggested qualification: correct a source with attached receipts, kill after `receipts`, resume after the original correction input is unavailable, and require identical retained receipt completion, exact surviving receipt values, and no repeated source processing or receipt pruning. Keep the current value/evidence checks; no broad fault framework is needed.

## Patch summary

The patch adds an `EvidenceSpec` operation that replaces complete receipt groups for stable source occurrences. Its input is retained Parquet with `source_file`, `source_row`, and an opaque typed `evidence` value. Optional deletion input contains the occurrence keys. Receipt values, duplicate rows, nulls, and nested order are retained. External URIs inside a receipt remain opaque and do not promise attachment custody (`src/evidence.rs:13`).

The operation uses the existing admission, processing, validation, readback, and guarded selection path. The selected result adopts the source and computed groups unchanged and carries a separate receipt table with actual removed/added rows (`src/engine.rs:1285`, `src/engine.rs:1437`, `src/engine.rs:1538`). Source corrections preserve surviving occurrence identities and prune receipts belonging to replaced or deleted occurrences. Incremental related refresh can adopt identical value and contributor tables while advancing exact input coverage.

Important callers are the embedded public methods (`src/engine/evidence.rs:106`), HTTP routes (`src/http.rs:34`, `src/http.rs:460`), CLI dispatch (`src/main.rs:556`), generic phase preparation (`src/engine.rs:978`), and source/refresh processing (`src/engine/write.rs:199`, `src/engine/incremental.rs:244`, `src/engine/aggregation.rs:259`). The transport additions call the same engine services.

## Data flow and invariants

1. **Input custody and identity.** The request declares BLAKE3 identities. `prepare_source` resolves retained processing first; otherwise it reuses admitted objects or copies and verifies new files (`src/engine.rs:830`, `:912`). Processing completion retains admitted inputs and the captured base manifest (`:1011`). The selected evidence result retains prior input records and appends operation-specific receipt inputs (`:1411`). Those references escape into the immutable result and retention inventory.
2. **Occurrence identity is distinct from business keys.** Receipt scope consists of file/row keys, not `id` values. Replacement preserves duplicate receipt rows, but its distinct scope replaces their complete occurrence group (`src/engine/evidence.rs:178`, `:201`). Value correction first preserves old origins; removed source occurrences then determine receipt removals (`:267`). Equal source values do not authorize keeping a corrected occurrence's old receipts.
3. **Value and evidence generations remain separate.** Evidence selection reuses the complete base `groups`, `computed`, and `related` values and leaves source `changes` absent (`src/engine.rs:1437`, `:1548`). `verify_groups` independently checks those equalities (`src/engine/backfill/verification.rs:192`). Receipt changes cannot silently impersonate source changes.
4. **Completed phases remain reusable and protected.** Receipt pruning saves output, removed/added tables, and exact source/prior-receipt dependencies before the injected stopping point (`src/engine/evidence.rs:249`, `:293`). Retry compares dependencies before adoption. Inventory recognizes the new phase and traverses those references (`src/engine/retention/inventory.rs:1135`). The final focused run also passes W2’s exact process-loss assertions; the completion-key correction above supplies the active lookup check missing from the initial trace.
5. **New evidence reaches dependent coverage.** Same-value incremental refresh retains its source and contributor table but carries the newly captured `VersionRef` in coverage. The unchanged-value shortcut is constrained by existing transform/schema qualification and guarded input succession (`src/engine/incremental.rs:59`, `:511`; `src/engine/refresh.rs:271`). It is valid for the implemented source-value transforms, not a declaration that an arbitrary receipt-dependent policy is unaffected.
6. **Backfill cannot overwrite new receipts.** Composition begins from the currently selected result; its source, related binding, boundary and target group must remain compatible. New evidence inputs must follow an explicit receipt/backfill parent chain, not merely equal row values (`src/engine/backfill.rs:657`; `src/engine/backfill/verification.rs:244`).
7. **Verification scope stays explicit.** Routine checks establish shape, references, counts and bounded samples. Deep checks establish the native change equation, source membership, and inherited receipt multiset (`src/engine/evidence.rs:373`, `:396`, `:406`). These checks do not assert that an opaque external receipt URI remains available or that application-specific evidence policy has run.
