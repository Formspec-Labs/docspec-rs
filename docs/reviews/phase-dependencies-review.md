## Findings and their disposition

The added optional `FileCompletion.source_metadata` captures that exact metadata only when work completes (`src/engine/backfill.rs:34`; `src/engine/backfill/preparation.rs:79`). Existing completions retain their original reference and legacy absence remains unknown. Keeping it outside `file_key` preserves valid reuse across metadata changes that do not change consumed values (`src/engine/backfill.rs:678`). The passing expanded test asserts the exact reference, then reorders the source schema and proves all retained file-completion records remain unchanged (`tests/phase_dependencies.rs:155`, `:177`, `:212`).

**F2 — test coverage, closed:** the initial test only deserialized a stripped `PhaseResult`. The expanded test commits an interrupted processing record without `dependencies`, removes the original external input, resumes, checks exact retained-input assembly and asserts `validation.dependencies == None` (`tests/phase_dependencies.rs:80`, `:94`, `:105`, `:116`). This executes the fallback and preserves unknown legacy state; it does not confer cleanup authority.

**F3 — build correctness, closed:** the `FileCompletion` literal in `aggregate_completion_descriptors_cannot_exceed_assembly_allowance` initially omitted the newly required `source_metadata` field. It now sets `source_metadata: None`, preserving the fixture's descriptor-capacity purpose (`src/engine/backfill.rs:962`). The reviewer verified the correction and its passing assertion in the completed all-target gate.

**Scope limitation, required before retirement:** `backfill-prepared` remains a `TablePin` and `backfill-validation` remains an `ObjectRef`; their source interpretation is not independently decodable from the hashed key (`src/engine/backfill/preparation.rs:31`, `:39`, `:158`). File-completion dependencies do not solve this for independently retained prepared/validation roots, including empty-source work. Those families need typed handling or must remain unknown to destructive maintenance. This is already identified in `retention-inventory-design.md`; no deletion is enabled here.

## Data flow and invariants

- New admission records explicitly have an empty additional dependency set; their retained copies or typed coverage remain in existing fields. New processing records bind the actual admission objects. The implementation does not infer those objects from a later material-key lookup.
- Reusing a completion preserves its captured input paths and schema identities. Build's cross-base reuse remains governed by the existing canonical schema/history identity, while Update and incremental Refresh retain exact bases in their existing change records. A different operation applies its own release input-name prefix without changing the original object reference.
- `None` means unknown legacy dependencies, not an empty complete dependency set. Evidence and validation propagate that unknown state through `Option::map`. Future maintenance must not infer deletion authority from the legacy assembly fallback.
- Schema-only references retain the metadata needed for field/default interpretation. Snapshot references additionally name snapshot and schema. Their physical closure must be expanded and checked by future maintenance; merely keeping the metadata file is insufficient. Existing `TablePin.objects` uses conservative all-referenced-snapshot inventory. This patch implements neither expansion nor a smaller deletion scope.
- The added work clones a bounded number of references per general phase and one schema identity per backfill file. The general phase path adds no payload read, hash, SQL execution, file inventory clone, lifecycle transaction, or ordinary-read validation. Backfill metadata grows with completed files and stays within the existing completion-bundling and lifecycle metadata limits; larger records can reach those limits sooner. No throughput or whole-process memory measurement is claimed.
