# R6 next step: explicit phase retirement and exact local removal

**Recommendation: implement exact-generation retirement first, then one bounded local removal transaction using the existing lifecycle and owned maintenance task. Keep removal disabled until both are qualified together.** This is architecture preparation, not approval to delete retained work.

Static review of `9c85a49` plus the current worker-custody changes. No Cargo, payload reads, or production edits were performed for this review. The controlling requirements are [R6, retention and recovery](../requirements/06-maintenance-retention.md), especially explicit phase retirement, fresh plan intersection, durable unavailability, and per-object reconciliation. The [inventory design](retention-inventory-design.md) and [worker design](retention-worker-design.md) explain the preceding decisions; current implementation, rather than those proposals, supplies the evidence below.

The user's newly supplied plan, **Object protection** (`/tmp/codex-remote-attachments/01a116b5-a9a6-7363-acec-cc4bcb984f9a/68780234-c3d4-40d0-9d50-bf5e235c2883/1-codex-plan-01a11900-ac52-77c2-81e4-70cf250b7570-01a11900-ac.md:31`), explicitly requires one protection owner and durable owner tokens before foreign references are selected. ## Smallest concrete implementation

Use one owning dataset per request, while checking protection across the entire owned catalog. This permits the decision in one guarded `Lifecycle::commit` without a cross-table transaction protocol. Do not retire `result/`, `readback/`, `backfill-readback/`, selected releases, seals, succession, or historical interpretation in this slice. Catalog-free readers therefore retain their present promise.

Add compact typed records in the existing lifecycle:

- An owner-side reference protection names the consumer, stable token identity, exact owned object/snapshot dependencies, and active/retired state. Keep attempt-prefix protection distinct. Acquire idempotently through the owner's guarded lifecycle before a consumer records a new durable foreign dependency; consumer completion/selection retains the committed token identities. Acquisition refuses an unavailable/removing target. Removal checks active owner tokens in the same guarded state. Resolve shared dependencies through their actual owners rather than treating a manifest's owner as owner of all referenced files. A crash between owner acquisition and consumer commit retains extra protection; it never creates a dangling reference. Reconcile or explicitly retire that token before releasing it.
- A retirement marker names the exact completion key and native revision, plan identity, and explicit reason. Scope it to its lifecycle table; the submitted plan also binds that table's identity and observed metadata. Preserve the original completion row and material key. Use a generation-specific marker key so a later recomputation cannot erase earlier retirement evidence.
- A bounded plan contains those generations, exact reservations to close, candidate `ObjectRef`s, any native registrations to remove, observed boundaries, blockers, and unique logical-byte estimates. Existing read-only inspection remains observational; it must not start reporting unmatched bytes as reclaimable.
- A removal intent contains only the exact freshly eligible subset, its plan identity, retirement/closure decisions, and required registration effects. Per-object outcomes are `deleted`, `already_absent`, or `failed`; absence of an outcome means unresolved. Keep failed removal resumable and unavailable. An error does not reactivate a retired completion.

Implement the flow beside `src/engine/retention.rs`, extending the existing inventory collector rather than duplicating its root dispatcher. Add strict handling for the new record families: retirement removes only that generation's recovery promise; intent/outcome metadata records an unavailable identity, not a reusable root. Every surviving phase, result, captured input, and reservation still protects its exact dependencies. Missing dependencies in a surviving legacy record remain a refusal. Explicit retirement must not silently upgrade unknown legacy evidence.

Owner-token acquisition belongs beside the existing input-capture/selection seams in `src/engine/inputs.rs` and `src/engine/refresh.rs`, with dependency capture in the common completion path. Do not add another database or claim a cross-table atomic commit: owner protection commits first, then the consumer binds it. Existing foreign references remain conservatively protected by the complete global inventory; do not fabricate historical tokens or infer their absence permits deletion.

Reuse changes cover `plan_request_admitted`, `phase`, `complete`, coordinated `groups/` acknowledgment, `plan_backfill_admitted`, and every file/prepared/validation lookup and acknowledgment in `backfill/preparation.rs`. Share one generation-aware lookup rule; do not scatter key-presence exceptions. Concurrent recomputations still keep the first active completion and its original provenance. Exact source/output comparisons prevent mixing generations; report dependent generations requiring retirement rather than silently retiring them.

### Preview and execute

1. Preview explicit generations/reservations and durable candidate identities. Candidates must be regular managed objects/native files inside the named owned attempt, with exact provenance. Exclude external input locators, arbitrary user paths, scratch/spill/cache, lifecycle/catalog files, and whole-directory deletion. Unknown provisional files remain out of scope; no orphan sweep or recursive payload inventory is required.
2. Execute in a private owned task holding `write_owned` on the existing maintenance gate, before dataset locks. Reuse admitted internal helpers; acquiring a public shared wrapper beneath this guard deadlocks. Drain ordinary work, validate reservation closure, and run the existing global collector with only the explicitly proposed exact generations/reservations omitted. Preserve all other roots.
3. Intersect the submitted candidates with fresh eligibility. New protections shrink the result; never add candidates. Refuse changed generation/registration identities. Reserve metadata/history capacity for intent and bounded outcomes before effects: `Lifecycle::commit` counts obsolete appended rows against its history limit (`src/catalog.rs:279`), so reserving only heap memory is insufficient.
4. In one guarded owning-lifecycle commit, recheck owner protections and persist exact retirement markers, reservation closure, and the removal intent. This is the same owner authority through which protection acquisition must conflict. Reconcile a lost commit response by intent identity before any deletion. A conflicting request under that identity refuses. No external effect occurs unless the exact intent is durably observed.
5. Perform only recorded registration/file effects, then retain bounded per-object outcomes. Reconcile after process death from that same intent; do not relist directories and invent replacement candidates. Repeated unchanged failures should not append unbounded duplicate history. Before each effect, retain enough admitted history capacity for its outcome.

For this first local slice, use **workspace-wide maintenance-only admission while an intent remains unresolved**, in addition to owner-token exclusion. The exclusive guard blocks new local work during execution; startup discovers pending intent before serving ordinary catalog work, and returned deletion errors leave admission closed to that work. A narrowly defined inspect/resume path remains available. Existing immutable release readers remain allowed because their objects cannot enter the removal set. This uses lifecycle intent as persistent authority, with an in-memory admission flag derived from it; it does not add a second registry or scan dependency graphs on ordinary reads. A failed cleanup temporarily delays unrelated catalog operations. More selective concurrent admission should require a demonstrated need, not precede this bounded implementation.

## Exact local effects and support limits

Use the maintained catalog's registration-only `drop_table`, with captured table identity and metadata-head checks, when removing an unused native registration. Record/reconcile that effect before deleting its metadata. The installed `iceberg-catalog-sql-0.10.1/src/catalog.rs:750` deletes registration; `:778` shows that `purge_table` also invokes bulk physical cleanup. Do not use `purge_table`, native bulk deletion, automatic expiration, or `remove_dir_all`. An unqualified registration is a blocker, not proof of ownership.

An `ObjectRef` digest is not an OS conditional-delete token. Qualify the local adapter's immutable-path and exclusive-writer assumptions, check owned ancestry/regular-file identity without symlink escape, and refuse replacement or conflicting identity. Capture/check the supported filesystem identity; if content qualification is needed, hash only that candidate at this destructive boundary using the existing verifier (`src/storage.rs:292`). Do not repeatedly hash retained payloads for reachability. Unlink the exact file, sync the affected directory under the supported durability model, and distinguish absent-after-unknown-effect from observed successful deletion. The existing creation fsync (`src/storage.rs:303`) does not establish deletion durability.

Scope remains the owned embedded catalog. Direct external filesystem/catalog mutation and injected/remote adapters are unqualified. Catalog-free readers/comparisons may have temporary spill work outside the catalog drain; their scratch is never a candidate. Keep all issued releases and current catalog recovery files. Restoring an old catalog image and replaying old deletion intent is unsupported until actual restore fencing exists; this slice cannot advertise point-in-time recovery or complete R6.

## Required checks before removal is enabled

- Exact retirement/retry/reopen, then recomputation at the same key: the new revision is reusable; the old one remains retired. Concurrent completion retains first provenance. Test general phases, scalar files, prepared/validation, and empty-source groups.
- Retire/recompute processing while validation/evidence remains: mismatched physical generations refuse or reuse the exact old qualified generation. No stale validation bypass. Original processing input bindings survive admission retirement.
- Shared references across datasets, phases, history/readback releases, and active reservations block physical removal. Retiring a promise can reclaim zero bytes. A new protection after preview shrinks execution.
- Race owner-token acquisition against removal reservation across two lifecycle tables: exactly one authorization wins; stale consumer selection cannot bind a removing object. Lose each owner/consumer response and stop between their commits; retries preserve the token, and excess protection remains until explicit reconciliation. Exercise these guarded conflicts directly so the global local gate cannot mask a missing durable rule.
- Cancel the executor and kill/reopen at intent commit, registration removal, unlink, directory sync, and outcome acknowledgment. Unknown responses reconcile; pending intent blocks catalog admission; a queued writer cannot create new references. Preserve catalog-free historical readback.
- Foreign/symlink/replaced files, unknown legacy roots, changed registrations, absent files, capacity exhaustion, and partial failures refuse safely. Prove no effects before confirmed intent and no automatic scope expansion on resume.
- Report logical eligible/protected/removed bytes separately from observed allocated-block and volume-space change. With candidates fixed, measure history/native-metadata work, outcome commits, maintenance wait, memory, and retained disk. The collector has bounded request state but still scans lifecycle history; no scaling result is claimed.

**Disposition: KEEP the existing Iceberg inventory and owned-task design; RESHAPE completion reuse around exact generations and implement guarded owner protections before deletion.** The concrete gain is reclaiming explicitly retired, unshared durable work without a new database, persistent reverse index, worker registry, or repeated payload validation. Defer release expiry, automatic sweeping, compaction, remote deletion, and restore execution; retain them as open R6 obligations.
