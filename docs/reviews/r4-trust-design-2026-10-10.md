# R4 local write trust and forward comparison design

**Verdict: RECONSIDER the trust boundary before adding chain execution.** Keep the existing applied-write relations, accepted succession, and shared comparison plan. Add a small versioned local production receipt, bind it to the exact selected result in the existing selection commit, and compose changes through maintained relational operators. Do not infer completeness from `ReleasePin.verified`, a structurally valid `ChangePin`, or accepted succession alone.

Static review of `0011f7588ab58171c0f3d71e829b4902215ab70b`, dated 2026-10-10. Scope: `docs/PLAN.md`, R4 with relevant R1/R5/R7 requirements, and the current write, history, comparison, verification, admission, and retention seams. Rust and semi-formal architecture review guidance applied. No other review reports were read. No implementation changes, builds, tests, formatting, benchmarks, commits, or corpus reads were performed. This review qualifies a design direction, not an implementation or performance result.

## Findings and decisions

### F1 — A validated result is not yet a complete applied-write certificate

**BLOCKER · unstated assumption · RESHAPE.** `ChangePin` has exact base and native-table references, keys, and removed/added tables, but no production-rule version, validation-rule version, completeness scope, or selected result identity (`src/model.rs:1079–1089`). `ReleasePin.verified` explicitly means routine validation/readback, not certification of all payload values (`src/model.rs:168–186`). Routine `verify_native_changes` checks counts, schemas, and new-table structure; the membership/reconstruction relation executes only in deep mode (`src/engine/changes.rs:93–185`, `187–200`). Therefore neither field can safely be reinterpreted as the new R4 trust claim, particularly when resuming old phases.

The code already supplies the stronger production premise needed for local trust: one joined decode is split into kept and removed rows, and the exact added files are shared by the result and added relation (`src/engine/write.rs:515–529`, `563–618`, `640–656`). Keep that construction. Persist its explicit semantics version with the producing completion; after ordinary output validation, retain the exact completion binding. At selection, issue a local certificate only from that recognized completion. An old routine completion without the production identity stays readable and takes full comparison; new code must not silently bless it.

Place the final certificate outside the release manifest. It can then bind the complete before and after `VersionRef`, including the already-created result manifest digest, without creating a self-referential manifest hash. Co-commit its link with `result/<id>` and `succession/<id>` in `select_with_progress` (`src/engine/history.rs:197–234`). Keep only bounded metadata in the catalog; the existing native relations remain the bulk evidence. The local catalog is the authority for issuance. A copied JSON descriptor or caller-supplied `verified` flag does not gain that authority.

### F2 — Chain rows must resolve to endpoint occurrences before value cancellation

**BLOCKER · commitment violation if omitted · KEEP identity semantics, RESHAPE chain input.** Full comparison currently operates on the two endpoints and groups by typed values, optionally including stable occurrence addresses (`src/engine/comparison.rs:334–359`, `489–496`). Its stream chooses deterministic surplus members through sorted `ROW_NUMBER` and signed aggregation (`441–483`). Feeding this operator a raw union of all intermediate additions/removals would change the premise: a surviving value representative can come from an intermediate version rather than either requested endpoint.

Compose by stable occurrence identity and typed values first. For a continuous sequence of complete local deltas, signed aggregation cancels intermediate members; surviving negative members belong to the requested before endpoint and surviving positive members to the after endpoint. Then apply the requested value or occurrence comparison. Keep the logical key fields through composition and validate their declared field IDs; one-to-many replacement means a business key can legitimately contain several occurrences. Do not implement “one old row and one new row per key” or deduplicate duplicate values. The replacement writer deliberately replaces complete key groups (`src/engine/write.rs:336–358`, `412–417`).

Apply that exact-occurrence reduction to **both full and accelerated addressed streams**, not only to chains. Otherwise, value mode can return a different valid endpoint representative than current full endpoint ranking: before has `x@b`, after has `x@a,x@b`, and `a < b`; current full ranking returns `x@b`, while the delta identifies `x@a`. Shared reduction makes both return `x@a`, then applies existing value ranking only to residual members. Occurrence mode emits the signed residual members directly and needs no ranking. Count-only value comparison can retain its cheaper address-free aggregate. This revises the full path's representative choice within the documented promise of deterministic surplus representatives, not causal deletion identity (`src/model.rs:745–753`). Qualify typed rows and addresses independently; count equality alone is insufficient. The extra aggregate and reduced sorting work are a structural tradeoff, not a measured speedup.

### F3 — Optional acceleration needs its own retention meaning

**CONCERN · intent versus shape · RESHAPE.** Current availability and retention include source and receipt `ChangePin` objects in the complete result closure (`src/engine.rs:2331–2348`; `src/engine/retention/inventory.rs:969–1005`). Routine/deep result verification also requires applicable changes (`src/engine.rs:2423–2432`; `src/engine/changes.rs:19–42`). A missing-file fallback in the new comparison planner alone would not deliver R4-T05: other consumers could still require those supposedly optional files.

Give the new change link an explicit optional-acceleration owner in the existing retention inventory. Required consumer or unfinished-phase bindings protect their chosen evidence separately. Retiring an optional accelerator must remove only its availability promise, not its immutable identity, source succession, endpoint values, or required receipt relations. Review `release_objects`, verification scope, and inventory traversal together before enabling its deletion. Existing retained formats/phase recovery must not lose required dependencies through a blanket change to inventory traversal. This is the required R4/R6 seam; it does not require a second retention system.

### F4 — Reuse the comparison plan internally for R5

**CONCERN · sibling conflict · RESHAPE.** Public counts and row streams already share `comparison_plan` (`src/engine/comparison.rs:72–75`, `165–169`). R5 `changed_keys` currently accepts only table pins and discovers changed physical files (`src/engine/incremental.rs:315–420`), so it lacks the selected-version and local-trust context needed to use the new accelerator. Calling public `changes` from inside refresh would re-admit work and reselect inputs; the reader wrapper specifically shares its existing maintenance guard to avoid reacquisition while maintenance waits (`src/engine/worker.rs:175–193`).

Expose a narrow internal admitted comparison input: exact releases, the captured lifecycle rows, chosen native representations, schema/identity interpretation, and the existing budget. Reuse the same plan for public comparison and R5 key discovery. R5 can project the union of old and new key values from endpoint changes, then recompute complete affected groups with its existing rules. Preserve the metadata effects even when the row relation is empty. Receipt, definition, and coverage changes are separate invalidation inputs, as R5 requires (`docs/requirements/05-dependent-refresh.md:15–25`); do not use value-mode cancellation to hide a new source occurrence from occurrence-dependent joins or evidence.

Three review hypotheses were tested against these traces: production already retains exact applied rows (confirmed); selected routine validation itself supplies the planned trust certificate (refuted); existing signed comparison operators can be reused unchanged over arbitrary chain rows (refined: endpoint-occurrence reduction must come first).

## Smallest complete local design

1. **Version one concrete local write claim.** Bind the operation/request identity, change subject or field group, exact before/after native interpretation, logical key field IDs, removed/added table identities, complete-applied-rows claim, occurrence semantics, and the material writer/validator rule versions. Use the retained `ObjectRef` digests and native pins; do not hash the whole historical payload again. A broad package or repository hash can remain provenance, but is not the sole invalidation rule. Do not add per-key catalog records, a generic certificate framework, or a global cache.

2. **Separate production completion from selected endorsement.** Preserve the production claim through the existing processing/validation completion and exact retry equality check (`src/engine.rs:1280–1290`). A recognized completion permits the selection code to create a bounded receipt with exact before/after `VersionRef` and a digest of its precise change description. The guarded selection transaction endorses that receipt alongside the result and succession. Require matching native commit revision and full endpoint identity when consuming it, following the existing `check_link_receipt` pattern (`src/engine/history.rs:321–354`). Do not make comparison reread retired processing payloads: retain the small validated scope/identity facts needed to interpret the endorsement.

3. **Capture one history snapshot for the comparison.** After exact endpoint admission and before payload planning, resolve the optional forward path from the requested after endpoint back toward before. Reuse bounded `SnapshotRows` decoding and revision checks. Comparison does not need to scan later selections from the live head merely to find a historical interval; `follows` has that stronger current-head requirement for R5 promotion (`src/engine/history.rs:95–128`). Keep that requirement in promotion. Validate each used link against its co-committed result and ensure revisions decrease, endpoint identities agree, and no unsupported branch is inferred. A readback that was never selected remains comparable through full reconstruction.

4. **Use explicit zero-change bridges.** Source receipt-only updates, independent enrichments, and other composition steps can bridge the source chain when the exact logical source pin is unchanged. Derive the empty source relation from that identity; retain each endpoint's metadata effects. A changed schema or definition is not automatically empty or comparable. An applied-write base must match the accepted predecessor's relevant logical group, not merely a composition parent chosen elsewhere. Compaction can select a different physical representation only through its existing qualified logical identity; it must not create a new logical event.

5. **Build bounded native relations, then reuse existing outputs.** Open only certified removed/added relations through the maintained occurrence reader. In both addressed full and accelerated paths, group by typed values plus stable file/row address, sum signed weights, and remove zero weights. This cancels unchanged/intermediate occurrences and preserves multiplicity. Occurrence mode emits those endpoint residuals; value mode uses the existing ranked cancellation over them. Keep the address-free value-count path when addresses are unnecessary. Charge retained descriptor/plan bytes and relation handles before constructing the plan; bound plan depth as well as decoded batches. Use maintained aggregate/sort spill and bounded chunks for supported long chains. When an optional acceleration planning limit is exceeded, select full comparison with a specific reason before emitting rows. Runtime read, decoding, integrity, or exhausted-resource errors must propagate; they are not permission to change to a successful empty result. Preserve the existing bounded-window admission checks where ranking remains (`src/engine/comparison/window.rs:23–95`).

6. **Keep metadata and qualification scope honest.** Add the actual accelerated path and structured fallback reasons to the existing `ChangeDescriptor`; continue calculating effects directly from requested endpoints (`src/engine/comparison.rs:499–539`). Unknown changed fields broaden to the complete relevant group. Initial/local support must say which writer versions, subjects, schemas, and identity modes are qualified. Portable certificate admission remains a distinct part of the accepted plan: possession of bytes and hashes proves neither authorship nor completeness. It needs an explicit trusted producer boundary or independent endpoint-membership/reconstruction qualification once at admission, then a retained exact-scope completion. A local receipt cannot satisfy that external check.

## Invalid versus unavailable evidence

Keep the planner's decision separate from errors: conceptually `ready relation`, `full fallback with reason`, or `error`. Do not implement `try_chain(...).unwrap_or(full)`.

| Observation in the evidence being considered | Required classification |
| --- | --- |
| `force_full`, reverse/unrelated endpoints, unsupported field group/schema transition, recognized but unsupported trust-rule version | Explicit full path/reason, subject to normal endpoint comparability. No attempt to infer order or upgrade trust. |
| No local certificate for an older result; optional link/accelerator explicitly unavailable or retired; absent optional accelerator bytes | Full fallback, with precise reason. An absent accelerator is not an absent source row. |
| Exact source logical identity unchanged through a valid selection step | Empty source change relation; retain schema/definition/evidence/coverage effects. |
| Relevant certificate JSON cannot decode, claims contradictory endpoints, has conflicting object identity, mismatched descriptor digest, wrong subject, invalid address/schema, or a selection revision different from its result | Refuse invalid evidence. Never convert to missing history. |
| A succession record is present but malformed, has impossible revision order, or contradicts its co-committed result | Refuse. A missing ordering proof can prevent acceleration; R5 promotion still refuses missing required succession. |
| Optional relation is readable but truncated, has a corrupt footer, fails decoding, has an identity mismatch, or violates complete-delta assertions | Refuse corruption. Do not treat a read error as legitimate retirement. |
| An endpoint or a required consumer evidence binding is unavailable | Refuse the requested operation; full comparison cannot reconstruct a missing endpoint or waive required evidence. |
| Resource exhaustion after execution starts | Preserve the actual error and completed work; no silent retry under different budgets or partial stream success. |

Missing-file fallback must recognize actual not-found/declared unavailability, not every I/O error. A present unsupported future version differs from a malformed record claiming a supported version. Check only evidence relevant to the selected path: forced full comparison is an independent endpoint operation, not an audit of all optional history. The routine trust model assumes immutable engine-owned storage; it does not claim to detect every same-size payload mutation without an integrity check. Explicit deep verification and external admission retain their stronger scope (`src/model.rs:178–186`; `docs/requirements/04-change-tracking.md:35`, `48`).

## Invariants, user value, and counterfactuals

| Invariant | Status and failure if omitted |
| --- | --- |
| Exact complete result is selected once by the guarded lifecycle commit | **Preserved** by co-committing the local change endorsement; a later separate write could lose or bind the wrong proof. |
| Routine work reuses durable checked outputs; deep reconstruction remains explicit | **Relied upon**, with a **new explicit local production scope**. Requiring a deep scan for each certificate or comparison defeats the small-update outcome. |
| Occurrence identity, multiplicity, and meaningful typed equality remain exact | **Relied upon**. Value-only early cancellation can hide replacements; per-key maps can drop one-to-many members. |
| Evidence, coverage, and definition changes remain visible independently of values | **Preserved** by endpoint effects and separate R5 invalidation; empty row changes cannot imply no work. |
| Succession is required ordering evidence; acceleration is optional | **Preserved by the proposed shape; current retention needs change**. Removing a change file must neither regress accepted order nor make endpoints unreadable. |
| Local completion does not establish portable producer trust | **Preserved** through explicit issuance scope; a copied manifest cannot inherit the local host's authority. |

The concrete improvement is fewer population reads for supported small updates and one shared discovery path for comparison and refresh. It adds a bounded production/selection receipt while reusing existing relations, atomic commits, native readers, DataFusion operators, and retention machinery. No speedup or memory bound is established by this review.

The counter-decision is to keep full endpoint comparison everywhere: simpler trust, but repeated population work remains and R4's user outcome is unmet. A deep re-verification before every accelerated comparison would retain most of that cost while adding chain complexity. A new event store or handwritten spill/merge engine has no identified requirement that the current primitives cannot express. Removing the optional acceleration should first affect latency and the reported path, never endpoint readability or R5 order checks. Six months from now, repeated deep verification, growing plan/metadata memory, or changes that remain undeletable would falsify the claimed benefit.

## Recommended implementation and qualification sequence

1. Define the versioned local production scope and descriptor/error semantics, including shared value representative normalization and one-to-many key meaning. Add the durable creation-time production binding and atomic selection endorsement. Qualify missing/forged/rebound endorsements, old completed processing resumed under new code, changed rule versions, interrupted validation, and lost selection responses.
2. Add the bounded chain planner inside the existing admitted comparison context; validate exact links and unchanged-group bridges before constructing payload plans. Preserve forced full, reverse, unrelated, and unsupported-schema behavior. Use one comparison plan for counts and row streams.
3. Add occurrence-first relational composition and the required value-mode policy. Independent fixtures must cover `A → B → A` with new birth identities, transient insert/remove, duplicate equal values, null/empty distinctions, whole-key removal, one-to-many shrinkage, changed logical keys, and compaction between writes. Assert endpoint membership and typed rows/addresses, not counts alone.
4. Route R5 discovery through the same admitted comparison input while retaining old/new key unions, complete group recomputation, exact contributor associations, evidence-only work, and accepted-source nonregression. Unsupported accelerators continue through the full discovery/rebuild path without reducing R5 scope.
5. Complete optional acceleration retirement against availability, verification, and retention together. Qualify active comparison lifetime, required consumer bindings, missing optional files, corrupt present files, endpoint readability, and retained succession after retirement.
6. Run the required targeted checks and repository gate, then preregister R4/R7 fixed-update and independent growth-axis measurements. Include cold/warm discovery, creation/validation overhead, unchanged/resumed work, long/hot chains, metadata/plan size, I/O, memory, and spill. Keep portable qualification and the remaining full accepted plan visible until their separate evidence exists.

**Final verdict basis:** intent matches the user outcome; the local write construction supports a small implementation; the current flags do not yet carry the required trust meaning. The proposed reshape preserves commitments and pays down duplicated discovery. Confidence is high in the static insertion points and semantic risks; resource and end-to-end performance remain unmeasured.
