# Explicit local physical cleanup: resources and native metadata review

**Recommendation: implement one owner-scoped, exact-object removal operation using the existing inventory, owned maintenance task, and native lifecycle. Keep every deletion route disabled until the reader, native-registration, durable-intent, and effect-recovery checks below pass together.** This would deliver actual local reclamation; another logical retirement increment alone would not.

Static architecture review of `77eb5611b71de7f6dc3da62b0ed5c8512a23572f`, applying the semi-formal architecture-review and Rust guidance. Code citations below refer to that commit, even if concurrent implementation moves the lines. No Rust edits, Cargo execution, tests, commits, payload deletion, or benchmark occurred in this review. The review owns only this document. The local dependency sources inspected are the pinned `iceberg` and `iceberg-catalog-sql` 0.10.1 sources in the Cargo registry.

## Findings that determine the design

### 1. Engine readers must protect their complete stream lifetime

**BLOCKER — ownership. RESHAPE the reader boundary before enabling removal.**

`Engine::read_group` and `read_evidence` currently delegate directly to catalog-free helpers (`src/engine/read.rs:11–24`). The returned native stream retains memory admission but no maintenance guard (`src/storage.rs:82–106`). The HTTP response retains the Engine, which preserves process ownership, but does not itself hold the maintenance read guard (`src/http.rs:412–424`). Therefore the existing exclusive maintenance guard can coexist with a live stream. A result whose independent availability has retired can become unblocked while that stream still needs another file.

Acquire shared maintenance admission before resolving the Engine read and move the guard, host ownership, and admitted request into the returned stream until end-of-stream or drop. Apply the same rule to combined and evidence reads. Recheck the exact available result inside that admitted boundary, closing the HTTP release-lookup/read-start gap. Reuse the existing owned-worker mechanism for preparation so canceling a waiting caller does not abandon native work. Do not reacquire the shared gate from an already-admitted internal operation while a writer is queued (`src/engine/worker.rs:110–183`).

Keep standalone catalog-free readers independent of the producing catalog. Their supported availability comes from an explicitly retained result or other durable root; a copied `ReleasePin` is an immutable identity, not an implicit forever lease. State that boundary in API/operating documentation. Arbitrary independent native readers are not drained by an Engine guard (`docs/STATUS.md:421–427`). This qualification does not implement remote reader leases or imply that an actively reading external program may be discovered automatically. R6 requires preserving promised readers, not creating a new distributed lease service (`docs/requirements/06-maintenance-retention.md:23–35`).

### 2. Removing payloads must not leave registered native tables unreadable

**BLOCKER — named seam. RESHAPE removal to include exact registration effects.**

Creation registers `data_<UUID>` native tables and retains them after producing immutable pins (`src/engine/write.rs:67–83`; `src/storage/tables.rs:81–104`). Current inspection lists namespaces but loads only each `lifecycle` table (`src/engine/retention/inventory.rs:116–146`). It does not establish what other registered native heads still name a candidate. The native inventory already follows every snapshot in a metadata file, live data/delete entries, and statistics sidecars (`src/storage.rs:369–449`). Checking only the native current snapshot or only whether its metadata JSON is a deletion target is insufficient.

Treat owned candidate registrations as construction bookkeeping, not additional permanent DocSpec result authority. The plan expressly selects complete results through the lifecycle rather than through independent native heads (`docs/PLAN.md:25–33`). Production immutable reads use `StaticTable::from_metadata_file`, not those registrations (`src/storage.rs:564–582`). Under exclusive local ownership, after supported workers drain, an obsolete registration can be detached without removing the immutable files that a retained pin still needs.

During preview, identify every registered head that would otherwise refer to a candidate and either preserve the candidate or include a qualified registration-only drop. Use a bounded, deduplicated native metadata pass with the existing inventory helper; include abandoned/uncompleted candidates, not just tables discovered in completed `TablePin` records. Record the exact identifier, UUID, and metadata location in the submitted plan. Fresh execution may use only those exact planned registration effects, and the intent records only their still-needed subset. A new referencing registration or a changed head discovered after preview must block its affected file targets or refuse execution; it must never silently add a drop. A new unrelated head neither expands the plan nor blocks unrelated candidates. Check recorded identities again before effects, including resume, and confirm or reconcile the drop before deleting any of that table's referenced targets. No effect may expand on retry.

Do not require every file named by a detached registration to be deletable: an obsolete table may name both unprotected A and protected shared B. Removing its catalog row and only A preserves B and retained static pins. Conversely, do not drop a native registration simply because its name matches `data_`; establish its ownership and supported construction state. An unknown registration or unsupported metadata layout is a blocker.

The pinned SQL catalog's `drop_table` removes its bookkeeping row only (`iceberg-catalog-sql-0.10.1/src/catalog.rs:750–775`). Its `purge_table` additionally calls `drop_table_data` (`:778–781`), bypassing this exact candidate scope. Never use purge, automatic native garbage collection, directory removal, or generic orphan sweeping. Existing native GC settings remain disabled (`src/storage.rs:67–75`). Existing metadata-log entries are historical metadata, not new selected snapshots; this review does not reinterpret them as advertised restore points (`src/storage/tables.rs:75–78`; `docs/STATUS.md:1467–1475`). Keep all lifecycle/catalog recovery files outside candidate scope.

### 3. Creation evidence proves the intended object; it is not a conditional unlink

**BLOCKER — unstated assumption. KEEP retained identity and qualify the final local effect.**

The existing owner code already proves exact creation identity from typed phase/result/grant records, and proves that a path lies inside its original owned attempt reservation (`src/engine/retention/owners.rs:604–640, 715–753, 766–847`). Retired records remain useful creation evidence. Reuse this proof in a batched traversal of the owner's rows. Do not call `qualified_object` independently for each candidate, which would repeat the owner-history traversal. Directory membership alone remains insufficient.

That evidence plus exclusive workspace ownership establishes the intended immutable `ObjectRef` within the cooperative local Engine model. It does not establish that an externally replaced or overwritten path still contains those bytes: `WorkspaceLock` is an advisory host lock, not filesystem object versioning (`src/budget.rs:157–190`). `check_object_available` checks file type and size only (`src/storage.rs:117–130`); same-size content changes pass that check. A digest in an `ObjectRef` is not an operating-system conditional-delete token.

For the requested changed-file refusal, perform one final bounded digest comparison for each still-present reserved target immediately before unlink, using the existing verifier (`src/storage.rs:258–300`). This is an irreversible-effect correctness boundary allowed by `docs/PLAN.md:44–46`; it is not a reason to rehash payloads during preview or reachability. Skip hashing absent targets and terminal completed retries. Checking only filesystem identity/size is a smaller alternative only if the supported promise explicitly assumes externally unmodified owned files; it cannot also claim same-size corruption refusal.

The local adapter must additionally reject symlinks, nonregular files, traversal, and escaped ancestry, and confirm the file being removed is the checked target. Check ancestors, not just the final path: current `validate_object` is lexical validation (`src/engine/retention/inventory.rs:1253–1266`). Unlink only the exact file and sync its parent directory before acknowledging durable absence; creation already uses parent sync but deletion needs its own effect rule (`src/storage.rs:303–311`). No current primitive atomically combines content verification with unlink against arbitrary outside writers. State that external concurrent filesystem mutation is unsupported rather than claiming that a hash or advisory lock fences it. A new general storage framework would not remove that local-filesystem limitation.

### 4. Bound history growth and proof work before effects

**CONCERN — debt and resources. KEEP the shared collector; batch work and reserve outcome capacity.**

Current inspection bounds candidate identities, queued/visited metadata, and claims; complete pins skip native re-expansion (`src/engine/retention/inventory.rs:396–420, 611–617, 669–759`). It reads owner bindings in one additional pass per owner, checking the previously observed metadata boundary (`:541–590`). Preserve those mechanisms. Run one fresh catalog-wide protection inspection for the bounded submitted set under exclusive maintenance, not an inspection per file. Reuse one bounded native inventory per distinct head for registration decisions. Never scan payloads or directories to discover new candidates.

Reserve lifecycle history room for the intent, unavailability markers, registration results, and bounded object outcomes before starting effects. `Lifecycle::rows` charges accumulated historical row bytes, not just the current values (`src/catalog.rs:205–249`); each commit charges the additional historical rows before writing (`:313–328`). Heap permits or a one-time preflight under exclusive maintenance do not preserve outcome capacity after restart and later commits. Use the owner-local durable reservation specified below. Keep failed attempts resumable, and avoid appending the same unchanged failure on every retry. Metadata-capacity refusal before effects is preferable to a delete that cannot subsequently finish its accounting within the configured history limit.

Do not add a reverse-reference database, filesystem crawler, persistent hash cache, scheduler, or worker registry. The existing explicit set and local maintenance barrier are sufficient for this supported scope. Native catalog listing allocates before application admission and native Avro parsing has its own allocations; existing checks are admission bounds, not a measured whole-process memory limit (`src/engine/retention/inventory.rs:305–310`; `src/storage.rs:452–467`). No latency or memory improvement is established by this static review.

### Owner-local history reservation decision

**Refinement for the next removal implementation: keep one `reserved_future_bytes: u64` field in each removal's current durable outcome/progress record.** This is an amount in the existing lifecycle replay-accounting units, not allocated Parquet bytes, memory admission, or filesystem free space. It supplements the exact immutable intent and outcomes already required by R6; it does not need a separate reservation table, persistent owner-total record, allocator interface, or global admission flag.

The minimal additional fields and state are:

- `reserved_future_bytes` in the current typed removal state, with checked integer conversion and addition. Include an exact `intent_revision` there if the outcome format does not already bind the original intent; the stable removal key alone must not bind a replacement intent. The intent already carries owner/table identity, exact files and planned registration effects.
- A private `reserved_future_bytes` sum in `SnapshotRows`, reconstructed from validated current removal states after cold replay. It is an acceleration of the same immutable native snapshot, like existing `history_bytes`, not a second authority (`src/catalog.rs:33–38, 192–250`). Do not sum historical versions of the reservation field.
- A removal-specific bound for the remaining outcome rows. Reuse the exact `history_row_bytes(key, encoded_value)` charge, including its record overhead (`src/catalog.rs:360–362`). Bound every possible persisted outcome encoding before effects, including JSON escaping, numeric widths and reservation-state updates. Prefer fixed error codes and bounded details to arbitrary OS error strings. Exact target identity can refer to the immutable intent's stable object/registration entries without copying every path into every retry outcome.

Every `Lifecycle::commit` on the owner's lifecycle must enforce the invariant below against the **proposed next state**, before its native write:

```text
H_after = H_before + charge(all rows appended by this commit)
R_after = sum(current reserved_future_bytes after these changes)
H_after + R_after <= configured lifecycle history limit
```

This includes ordinary owner commits, new removal intents, reservation top-ups, failed reports and terminal outcomes. An outcome and its justified reservation reduction land in the same guarded native commit. Do not first check `H_after + R_before`, which could prevent a valid completion from consuming the room reserved for it. On the warm path, update the cached sum using only changed removal-state keys; on cold replay, reconstruct it once from current states. There is no need to scan all history or all removal intents again on every ordinary commit. The existing expected-head guard and native atomic commit supply the concurrency and lost-response boundary (`src/catalog.rs:306–355, 416–438`). A stale preflight must retry from fresh state, never carry a stale capacity calculation forward.

Validate reservation membership and its required minimum against the original intent and retained outcomes. A pending intent without its corresponding state, a missing reservation field, a malformed value, an under-reserved pending state, or overflow is a refusal, not zero reserved bytes. Ordinary callers cannot erase another removal's reservation by supplying a smaller scalar. Successful completion releases its reservation only with the corresponding durable terminal outcomes. A lowered configuration limit cannot discard an existing reservation; refuse affected owner work until its declared capacity again fits. Unrelated dataset lifecycles remain independently usable.

**Failure rule:** a `failed` effect remains pending and unavailable, so recording it must preserve enough reservation for a later terminal result. One scalar is sufficient: derive a conservative terminal-outcome floor from the bounded original effect set and current outcomes. Before an effect round, reserve both its maximum newly appended outcome/state charge and that terminal floor. The outcome commit consumes its actual charge while retaining the floor for unresolved effects; an all-terminal commit releases the remainder. Use one bounded batch of outcomes per round where practical, rather than rewriting a growing result after every individual file.

A subsequent round must top up that same scalar, through a guarded owner commit, if its remaining reservation cannot cover another bounded outcome batch plus the terminal floor. The top-up row itself counts toward `H_after`. Refuse before additional deletion if capacity cannot admit it. Identical failed outcomes with unchanged state append nothing and retain the existing allowance. Native append history preserves changed failures; no finite allowance can promise unlimited distinct retry-history growth. A crash after an effect can still reconcile and persist the reserved terminal outcome without another effect or top-up. This prevents a failed report from consuming the last guaranteed completion bytes.

The pinned catalog already provides the maintained primitive needed here: an expected-head/compare-and-swap commit of the lifecycle rows. Its SQL update advances the metadata pointer only if the previous pointer still matches (`iceberg-catalog-sql-0.10.1/src/catalog.rs:973–1020`). The inspected adapter does not know DocSpec's serialized-row replay limit or reserve space for a future application outcome. Add this narrow accounting check to the existing lifecycle commit/cache, not a generic reservation framework. This reserves application history capacity; it cannot guarantee future disk space, credentials, or successful native I/O.

This decision supersedes the earlier proposal to leave the entire workspace in maintenance-only mode while an intent is pending. Hold existing exclusive maintenance admission during each actual proof/effect round. Between rounds and after restart, permanent owner-side unavailable markers prevent new references to its targets, and only that owner's reserved history constrains its ordinary commits. Pending-removal discovery supports inspect/resume without a new lease service or a persistent blockade of unrelated datasets. All supported reference-creation paths must honor the same unavailable markers before this narrower scope is enabled (`src/engine/retention/owners.rs:401–418, 660–663`; `docs/requirements/06-maintenance-retention.md:29–31`).

Use a single owning dataset per request so one native lifecycle commit can reserve all target objects. The submitted plan contains exact candidate identities, observed lifecycle and native boundaries, reason, blockers, registration effects and deduplicated logical-byte estimates. It does not itself retire other promises. Execute in the existing private owned maintenance task, before taking dataset locks, and call already-admitted internal helpers to avoid lock re-entry (`src/engine/worker.rs:135–183`).

After fresh proof, one owner commit records the exact eligible subset, stable removal ID and unavailability markers. A lost response must reconcile that exact intent before any side effect. The collector must validate the relationship between markers, intent, registrations and outcomes; accepting a marker's path alone is inadequate. Surviving roots stay roots. Removal metadata describes unavailable objects and pending effects, never new reusable content.

Reconcile pending intents after restart and expose inspect/resume. Keep permanent per-object unavailability after both success and failure; a failed unlink must not reactivate the object. Pending state reserves history in its owning lifecycle and blocks new references to its exact targets; it does not close unrelated dataset admission. Reconstruct the reservation from that owner's native rows when needed, and recheck all supported adoption/retry paths against durable unavailable state. The existing exclusive maintenance guard covers each actual execution round. Do not add a second authoritative pending-work store or a reader-lease service.

Perform only recorded registration and file effects. Confirm affected registration removal before removing its dependencies. Record `deleted`, `already_absent`, and `failed` truthfully; absent after a crash is not proof that this invocation deleted the file. A terminal recorded result is returned on retry without another unlink, hash, or root scan. Failed/pending work can resume the same identities, with fresh safeguards and no added targets. Account for failures using native append history rather than an additional journal.

## User value, alternatives, and verdict

The user-visible gain is ending storage growth from deliberately retired, unshared durable outputs. The conceptual cost is an exact pending-removal record and effect outcomes in the existing lifecycle, plus full stream admission and a thin local effect adapter. The operation pays down retention's current gap without another database or scheduler. A design that only emits more inspection or retirement records while files remain allocated fails this value claim.

The opposite decision—treat every native registration as an eternal root—would keep native tables readable but prevent useful reclamation because completed candidate registrations persist. Ignoring registrations would reclaim bytes while leaving native table reads broken. Registration-only detachment reconciled with exact file effects is the smaller coherent choice. The existing inspection partially supplies this capability; it cannot be relabeled as a remover because it explicitly does not certify unmatched objects reclaimable (`src/engine/retention/inventory.rs:75–80`).

The kill criteria are a promised stream failing because cleanup removed its next file, a stale plan expanding its effect set, a native purge bypassing protection, or an unknown effect restoring availability. A future reviewer should reject per-file full catalog scans, a repeatedly hashed whole graph, or a new reverse-index framework added without a measured bottleneck. Compaction, restore points, expired external-reader windows, automatic sweeping, injected/hosted catalogs and complete R1–R7/Comments qualification remain separate open obligations.

**VERDICT: RECONSIDER the bare “unmatched ObjectRef → unlink” boundary; APPROVE the explicit local removal shape described here for implementation and qualification.** Intent and user value match R6; commitment status depends on closing the blocker findings together. Existing primitives partially subsume the work. Confidence is high for the traced local seams and medium for deletion durability until the crash and filesystem-effect cases are executed. This is not approval of unreviewed implementation, hosted support, or completion of the full plan.
