## Smallest useful next work

The required next action already follows `completed` plus `required_phases`; adding another derived `next_action` string buys little. This closes discoverability without new persistence or reads.

**One narrowly useful plan improvement, if implementation is desired:** expose where reused durable work came from. Add `reusable_phase_origins: BTreeMap<String, RetainedGeneration>` to `RunPlan`, using the existing `{ key, revision }` type (`src/model.rs:546`). Populate it from the same `phase_key` and cached lifecycle revision used by `completion_with_reason` (`src/engine.rs:530–579`; `src/engine/retention/retirement.rs:339–360`). This lets a caller connect “processing reused” to its exact inspect record and its original operation, consumed-input references, metrics and runtime provenance. It requires no new query, decode, native metadata read or phase-result copy. Preserve the readback/result early return: name only the durable evidence it actually resolves, rather than reopening retired earlier phases. Do not expose all output/file lists again in every plan. This remains an evidence link, not a consolidated live status claim.

Falsifying test: extend the existing rebound-input/cross-operation reuse scenario so the plan names the original processing record and its native revision, even though the request's producer path and latest admission copy differ. Remove the original producer input, assert plan still works, assert lifecycle rows are unchanged and work-entry observations remain empty. Existing CLI/HTTP serializers need no new route; one existing transport plan assertion is sufficient.

A held-stream fixture can prove a progress event precedes completion and no completion is claimed after failure; retained phase reuse must emit reuse without writer events. Process RSS/scratch/request observations remain separate measured qualification work until implemented on that necessary path.
