# Remaining remote maintenance/restore boundary

Decision: do not expose remote removal or restore by removing the existing owned-catalog gates. The local journal/root rules are reusable, but configured R2/Basin lacks a implemented and qualified destructive-authority handoff in DocSpec. A normal S3 delete adapter alone cannot satisfy Q6.

Read-only investigation; no provider calls, secret reads, builds, shared source edits or implementation. Provider statements below use official documentation checked 2026-10-11; no runtime capability is inferred from docs.

## Accepted obligation

R6-T04/T05 require common exact roots, fresh eligibility, atomically unavailable removal reservations, exact effects/outcomes and reconciliation. R6 catalog recovery protects required bytes and cannot revive metadata promising deleted objects. Q6 explicitly resumes an old publisher/deleter after handoff or restore and requires storage to reject obsolete authority even when its old expected-pointer token matches. Catalog checks or a local test double are insufficient.

## Existing code that can be reused

- `engine/retention/removal.rs:127,259,274,313` runs existing preview/effects under owned-host exclusive maintenance and the owned-catalog guard. RemovalIntent records exact candidates, native registrations, original boundaries and outcomes; fresh reservations are durable before effects. Owner-side `owners::available` (owners.rs:402) refuses reference/grant admission after an exact removal reservation. Recovery and outcome capacity are already shared.
- `removal.rs:842–872` verifies exact native registration UUID/metadata, drops it, and reconciles catalog absence. `removal.rs:779` then calls only local `remove_owned_file`; unresolved absence reconciliation is local as well. RemoteObjects has configured bounded reads and create-only publication, but no remote delete/identity+authority method. A maintained S3 transport addition would reuse this journal rather than create another.
- `worker.rs:13–39` Host owns a filesystem WorkspaceLock and host instance. The owned worker/reader gates protect that one workspace. A second host connected to the same remote catalog is not excluded by this lock; there is no storage enforcement of the host instance on S3/catalog requests.
- `retirement/retirement.rs:681` refuses injected catalogs; `inventory.rs:178` assumes the embedded flat catalog and a lifecycle table in every enumerated namespace. Remote source reads already traverse strict configured release parents, but destructive inventory still needs qualified bounded owned namespace enumeration and complete supported root families, not a prefix listing/age rule.
- `engine/restore.rs:339–475` assumes a retained SQLite catalog image, verifies/restores exact local files, vacuums a fresh generation database, independently verifies saved registrations/rows, fsyncs and selects the local catalog pointer. `restore_catalog` at478 refuses injected catalogs. Remote REST catalog registration is not a replacement for the atomic local catalog-generation selection or the old-host fence. No remote saved-catalog image/restore procedure currently exists.

## Provider primitives and limits

[R2 S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/) documents DeleteObject and non-versioned bucket support (GetBucketVersioning is unimplemented). It does not document a DocSpec authority epoch carried into deletion. The DeleteObject row does not establish a conditional content-identity delete guarantee; do not infer one from conditional GET/PUT. A HEAD/hash followed by ordinary DELETE alone is not an atomic identity check.

[R2 temporary credentials](https://developers.cloudflare.com/r2/api/s3/temporary-credentials/) provide expiration, operation restrictions and exact-object/prefix restrictions using standard session tokens. [R2 authentication](https://developers.cloudflare.com/r2/api/tokens/) says account tokens remain valid until revocation or expiration. Those are candidate maintained fencing mechanisms. These pages do not establish ordering for already accepted/in-flight requests across revocation/expiration, nor make DocSpec's epoch effective at the provider automatically. That is a qualification dependency, not proof that the provider cannot support the required procedure.

[Basin deleting data](https://developers.cloudflare.com/basin-catalog/deleting-data/) distinguishes plain table drop (catalog detachment, retaining files) from purge, snapshot expiration and orphan removal (destructive). Plain detachment aligns with the current registration-first journal, pending exact REST-adapter runtime qualification. It does not itself authorize removal of DocSpec-required history or restore authority. [Manage catalogs](https://developers.cloudflare.com/basin-catalog/manage-catalogs/) documents independent compaction/snapshot expiration and their service credentials; neither tracks DocSpec's separate result/phase/foreign-grant roots. Enabling automatic expiration is not a substitute for common inventory.

## Smallest practical sequence

1. Freeze a narrow owned remote catalog/source-only maintenance profile: one explicitly controlled writer/deleter authority and known advertised reader availability policy. Qualify bounded namespace enumeration, exact native detachment without purge, root completeness and new-reference reservation races using the existing inventory/journal. Pure preview/logical retirement may be a smaller non-destructive first increment, but must keep unsupported roots conservative/refused and cannot imply remote deletion/restore support.
2. Qualify an actual provider credential-fenced handoff before exposing DELETE: old actor uses only operation/path-scoped, nonrenewable authority; recovery removes that authority and proves delayed old requests fail. Include a request accepted before handoff and delayed response/effect, not merely a request sent after token expiration. Reuse explicit secret/config resolution and maintained session-token support, with no ambient parent credential in the old actor. An operator-controlled revoke/drain profile may be sufficient if runtime evidence establishes its full boundary; do not add a speculative lease service.
3. Add one shared configured exact delete/absence reconciliation dispatch to the existing RemovalIntent executor, only once the immutable identity and fenced-authority profile are established. Retain unknown outcomes and losing prefixes; use no sweep and no purge.
4. Remote restore additionally needs a declared complete catalog capture and atomic recoverable selection procedure plus old catalog-write/destructive authority revocation. Current REST catalog load/register/drop calls do not implement a coherent all-table restore generation. Choose and qualify the provider handoff procedure first; then reuse existing point closure and intent rules. Copying backups to the same URI while old credentials remain live fails Q6 regardless of content hash/expected metadata CAS.

No framework or new record family is justified yet. Concrete prerequisite is provider-enforced authority and coherent remote catalog restore selection, followed by runtime qualification; it is not a missing local retirement marker. Local tests and successful remote Build/Update/export do not establish these destructive capabilities.
