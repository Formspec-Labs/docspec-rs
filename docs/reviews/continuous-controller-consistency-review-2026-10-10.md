Original severity: WARNING. Category: correctness / malformed metadata. Confidence: high.

### F2 — Focused race and field-identity regressions: closed by inspection

Original severity: WARNING. Category: test coverage. Confidence: high for the assertions; execution unverified.

The added controller tests force an optimistic worker to finish while the same parent owns a live fence and require parent completion, child result, authority selection and the adopted token's close to share one native revision (`src/engine/backfill/continuous/tests.rs:90`). They also retain a captured intent across abandonment or completion and refuse subsequent fence acquisition without metadata mutation (`:140`, `:177`). The native integration case starts with an absent target, rebuilds the source with reordered string columns, proves that an old field ID now names the other same-typed column, and requires `backfill_source_identity_changed` while preserving completed work (`tests/continuous_backfill.rs:796`). These cases cover the specific repairs raised during review.

### F3 — Completed-result child validation: closed

Original severity: WARNING. Category: correctness / malformed metadata. Confidence: high.

Completed parent execution previously resolved its result before validating the winning child's admitted request, while planning refused the same corrupted association. `continuous_result_in` now calls the shared `continuous_child_in` for the exact winning child before validating the parent completion or returning its result (`src/engine/backfill/continuous.rs:347`). This checks the request, admission, parent and predecessor associations using retained metadata. The regression now corrupts the retained request after both readback and selection, requires plan and run to refuse, and checks unchanged metadata and selected output (`src/engine/backfill/continuous/tests.rs:211`). The fix closes the inconsistent acceptance boundary without reopening source payloads; execution was not performed by this reviewer.

## Patch summary

The patch adds one immutable parent intent over existing fixed-capture scalar backfill operations. A child names an exact selected source and admission boundary. The controller resumes that child while its capture remains current, or records a successor and abandons the obsolete child. Existing per-file work, assembly, validation, readback, provenance and protection remain owned by the existing backfill implementation.

After bounded optimistic attempts, the local controller stops new source admissions, lets already-admitted work finish or be explicitly abandoned, and selects against the resulting boundary. The selected child result and parent completion share the existing dataset transaction. A live parent-owned fence is closed in that same transaction. CLI and HTTP additions delegate to the same engine service (`src/main.rs:679`; `src/http.rs:696`).

The relevant requirements are exact authored field identity and interpretation, atomic output/coverage, complete source catch-up, strict cutover and bounded intake fencing in `docs/requirements/03-schema-backfill.md:11`, `:35`, `:41`, `:43`; retained expensive work and unified protection in `docs/PLAN.md:69`, `:84`, `:96`.

## Data flow and invariants

| State | Creation / mutation / use | Required invariant and evidence |
| --- | --- | --- |
| `Intent` | Compiled from the original selected source; persisted with first child admission; read on every resume. | The caller's parent ID cannot change recipe or budget. Authored field IDs refer to the original meaning, not a newly reused display name. Request digest checks and the native source guard enforce this (`continuous.rs:383`, `:947`). |
| `Child` and current state | Deterministic ID from parent digest, round, exact source reference and admission boundary; state advances with successor admission. | A new capture cannot silently reuse the old operation identity. The previous child's abandonment and the successor's admission share the transaction (`continuous.rs:672`). |
| File/assembly/readback completions | Produced by shared scalar preparation; referenced by actual winning child; retained across parent retries. | Coverage advances only with completed scalar outcomes. A stale capture does not delete successful work; new captures can reuse unchanged file completions and preserve original execution evidence (`backfill/preparation.rs:154`, `:225`, `:265`; `tests/continuous_backfill.rs:180`). |
| Source admission boundary | Advanced by new Build/Update/Refresh admissions; checked against the selected source plus the complete admission proof. | Every accepted source operation must appear in accepted history or have an exact abandonment. A later full build cannot silently discard unfinished admission (`history/admissions.rs:48`, `:111`). |
| `SourceFence` | Acquired under the dataset lock, bound to local host/token/deadline; closed on selection, abandonment or cleanup. | New intake refuses; accepted work may drain. Retry never extends a live generation. Expired/previous-host tokens no longer stop intake, and stale cleanup cannot close a successor (`intake.rs:35`, `:109`, `:197`). |
| Parent completion | Added to the selecting transaction with child result, authority, succession and any live owned-token close. | Lost responses resolve the exact selected child. Mutable later source movement does not redefine this parent result. Availability retirement is still honored (`continuous.rs:322`; `history.rs:235`). |
| Retention and restore | Control pointers add no independent payload promise; shared child phases/results and their existing protections supply the object closure. | Superseding or abandoning a child does not delete its expensive outputs. Restore captures lifecycle metadata and existing protected objects; its new host invalidates former-host lease liveness (`retention/inventory.rs:279`, `:1524`; `restore.rs:179`, `:387`; `worker.rs:21`). |

The service continues to use the existing scalar file-completion cache, request protection, input proof, and selection transaction. This is a concrete simplification over a second processing or progress subsystem. The review establishes code reuse and bounded control structure, not measured throughput or storage savings.

## Reasoning record and conclusion

The initial hypotheses were that shared fixed-capture preparation preserved completed work; target-history checking prevented competing same-target selection; an exact local token bounded new intake; and parent completion could be reconciled atomically. Shared preparation/recovery was confirmed. The fence hypothesis required the same-parent adoption, expiry and abandonment repairs described above. The original target proof needed the additional native source-field correspondence check for new targets. Restore/protection integration is supported by the shared inventory trace and the new test assertions; execution remains unverified by this review.

The final target-receipt changes were also reread. Source request fingerprints deliberately omit relocatable input paths (`src/engine.rs:2057`), so `read_target` now compares material fingerprints plus explicit dataset/operation identity. Source operations do not uniformly populate optional `Operation::base_manifest`; resolving the declared base's earlier verified result preserves the parent check without refusing legitimate admitted Build/Update work (`src/engine/history/target.rs:162`, `:208`). These repairs were reported by the implementation owner following integration failures, then statically verified here.

The two final decode-reservation follow-ups are closed by recheck: `continuous_child_in` reserves its optional previous child before `validate_child` decodes it (`src/engine/backfill/continuous.rs:198`), and completed-result resolution reserves the parent, completion, winning child and succession records before completion validation (`:350`). The winning-child validator performs its own bounded dependency reservation. This establishes explicit admission accounting for these decoded copies, not a measured heap bound.

The repaired controller paths match the intended local consistency design in the inspected traces. F1–F3 and the final reservation follow-ups are closed by code/test inspection.
